# PDF부터 검토 결과까지: ReviewDocument를 두는 이유

작성: 2026-09-13. 업데이트: 2026-09-20. 비개발자용 설명이며 현재 구현과 향후 계획을 구분합니다.

## 전체 흐름

```text
원본 PDF
  ↓ XML 추출기: 글자와 태그·표·목록·그림 등의 구조를 읽음
추출 XML + 추출 품질 보고서
  ├─ 기존 Markdown writer → 사람이 PDF와 대조하는 MD
  ↓ XML adapter + 품질 검사
ReviewDocument: 여러 검토 기능이 함께 읽는 표준 문서 데이터
  ├─ 체크리스트 DB 검토 → 검토 결과 데이터 → Excel / JSON  [현재 연결 중]
  ├─ Before/After 비교 ← 이전 PDF의 ReviewDocument         [향후]
  ├─ 사양 반영 검토 ← 회사 시스템의 모델별 사양 데이터       [향후]
  └─ 다국어 QA 참고 의견 ← 번역 기준 영문과 대상 언어 문구   [향후]
```

현재 MD는 기존 XML 추출기의 writer가 만듭니다. MD를 다시 읽어 체크리스트 검토나 Excel을 만드는 구조는 아닙니다. 나중에 ReviewDocument를 이용하는 MD 보기를 만들 수도 있지만, 현재 MD 생성 경로를 교체했다는 뜻은 아닙니다.

## 현재 두 브랜치가 나뉜 이유와 역할

현재 Git 저장소에서 주로 보는 브랜치는 두 개다. 폴더 이름이 비슷하지만 맡은 일이 다르다.

| 브랜치·작업 폴더 | 현재 책임 | 현재 상태 |
|---|---|---|
| `feature/xml-markdown-review` / `xml-markdown-review` | PDF에서 Semantic XML과 사람 검수용 Markdown을 만드는 최신 추출기 | 여러 바이어·언어, RTL, BOOK, 문단 소속과 원문 복구 수정이 계속 반영된 최신 추출 소스 |
| `codex/xml-review-v2` / `xml-review-v2` | XML adapter, ReviewDocument, 체크리스트 근거 조사, JSON·Excel, 화면·배포 | 분기 당시 XML 추출기 기준본을 포함하지만 이후 최신 추출기 변경은 아직 미통합 |

2026-09-10에 `xml-review-v2`는 XML 추출기 커밋 `840512002a80a12b19c712116530ab69b1459c3a`에서 분리됐다. 이후 한쪽에서는 여러 PDF의 XML/MD 품질을 계속 개선하고, 다른 쪽에서는 당시 고정한 추출 결과를 기준으로 ReviewDocument와 체크리스트 연결을 개발했다. RTL만을 위해 분리한 것은 아니다. 추출기가 계속 바뀌는 동안 adapter·DB·Excel·배포까지 동시에 흔들리지 않게 한 작업 분리였다.

현재 관계는 다음과 같다.

```text
feature/xml-markdown-review
  └─ 최신 PDF → XML + 사람 검수용 MD

codex/xml-review-v2
  ├─ 분기 당시의 PDF → XML/MD 추출기
  ├─ XML adapter + 품질 gate
  ├─ ReviewDocument
  ├─ 체크리스트 근거 조사
  └─ JSON / Excel / 화면 / PC 배포 파일럿
```

다음 통합에서는 최신 추출기 변경을 `xml-review-v2`에 병합한다. 같은 추출기의 구·신 버전을 두 벌로 계속 운영하지 않는다. 병합으로 기존 추출기 경로를 최신 코드로 갱신하고, 의존성 검사를 통과한 뒤 사용하지 않는 과거 GridCell 실행 경로를 별도 정리한다. 병합과 과거 코드 삭제는 한 번에 처리하지 않는다.

## Adapter와 검토 Agent는 이미 코드상 분리돼 있나요?

책임은 이미 여러 모듈로 나뉘어 있지만 각각이 별도 저장소·worktree·프로그램으로 실행되는 것은 아니다. 한 `xml-review-v2` 저장소 안에서 `ReviewService`와 통합 실행 코드가 순서대로 호출한다.

| 단계 | 대표 코드 | 책임 |
|---|---|---|
| XML adapter와 표준화 | `review_document.py`, `semantic_xml_reader.py`, `xml_review_gate.py`, `xml_review_run.py` | XML을 검증하고 원문·구조·근거를 ReviewDocument로 보존 |
| 체크리스트 검토 | `checklist_observation.py`, `item_review_service.py`, `review_service.py` | DB 기준과 ReviewDocument를 대조하고 근거·미지원 사유를 기록 |
| 결과 통합 | `combined_review_run.py`, `combined_review_service.py`, `combined_review_model.py` | 일반 체크와 항목별 결과를 한 실행 결과로 묶고 완료·실패 상태를 관리 |
| 결과 표시 | `combined_review_view.py`, `combined_review_workbook.py` | 결과 데이터를 사용자용 Excel 표시값으로 변환 |

따라서 adapter는 체크리스트 Agent 내부에 섞인 것이 아니라 앞단의 공통 변환 계층이다. 현재 구현된 검토 기능이 체크리스트 경로 하나뿐이라 전체가 하나의 큰 Agent처럼 보일 수 있다. 앞으로 추가하는 검토 기능도 별도 worktree로 만들기보다 같은 저장소에서 독립 모듈로 두고 ReviewDocument를 공통 입력으로 사용한다.

구조상 `Agent`는 반드시 LLM이나 독립 실행 프로그램을 뜻하지 않는다. 여기서는 하나의 검토 목적과 기준 데이터를 가진 독립적인 검토 기능을 뜻한다. XML adapter는 검토 Agent가 아니라 모든 Agent가 함께 사용하는 표준화 단계이고, ReviewService는 Agent들을 순서대로 실행하고 결과를 취합하는 조정자다.

## 통합 후 목표 구조와 현재 구현 상태

```text
PDF
  ↓ 최신 XML 추출기
Semantic XML ──→ 사람 검수용 Markdown
  ↓ XML adapter + 품질 gate
ReviewDocument
  ├─ 체크리스트 DB 검토 Agent                 [현재 파일럿 연결]
  ├─ Before/After PDF 비교 Agent              [향후]
  ├─ 회사 시스템 모델·사양 비교 Agent          [향후]
  └─ 다국어 의미·맞춤법 QA Agent              [향후, 참고 의견 전용]
  ↓ 공통 결과 취합
JSON + 사용자용 Excel
```

각 검토 Agent는 PDF나 XML을 제각각 다시 파싱하지 않는다. `ReviewDocument + 해당 Agent의 기준 데이터`를 입력받고, 공통 결과 형식으로 근거·차이·미확정 사유를 반환한다. Excel writer는 검토 규칙을 가지지 않고 이 결과를 표시한다.

현재 체크리스트 연결은 ZC ENG 파일럿 범위의 근거 조사다. 문구를 찾았다는 이유만으로 업무 Pass/Fail을 확정하지 않으며, 아직 Before/After·회사 사양·다국어 QA 결과를 함께 생성하지 않는다.

## 다음 개발 순서와 체크리스트 DB 재정립 원칙

권장 순서는 다음과 같다.

1. `feature/xml-markdown-review`의 최신 추출기를 `codex/xml-review-v2`에 병합한다.
2. 이식성 경로를 정리하고 XML 추출기 전체 테스트를 통과시킨다.
3. XML → ReviewDocument 원문·구조·근거 보존 회귀 테스트를 수행한다.
4. 기존 checklist master를 별도 보존하고 v2 작성용 master를 재정립한다.
5. 체크리스트 검토 결과의 공통 데이터 계약을 안정화한다.
6. 안정된 결과 데이터를 이용해 사용자용 Excel/JSON을 고도화한다.
7. 대표 PDF로 사람 검토를 받고 지원 바이어·언어를 단계적으로 확대한다.

DB를 “현재 추출된 텍스트를 그대로 모아 새 DB로 자동 생성”하지 않는다. 기존 master에는 사람이 정한 업무 요구사항과 출처가 있고, 추출 텍스트에는 특정 PDF에서 관찰한 실제 문구와 구조가 있다. 둘을 대조하여 각 행을 다음처럼 분류하고 사람 검토 후 v2 master에 반영한다.

- 그대로 유지할 공통 업무 기준
- 현재 원문 단위에 맞춰 여러 item으로 나눌 기준
- 바이어·언어별 문구 변형
- 모델/회사 시스템 값 비교 Agent로 이동할 항목
- 더 이상 사용하지 않거나 근거 확인이 필요한 항목

기존 master는 덮어쓰지 않고 복구 기준으로 보존한다. v2 master의 안정된 ID는 업무 기준을 가리키며 XML node ID를 사용하지 않는다. 새 PDF 근거는 PDF 파일명·페이지·XML 위치와 함께 실행 결과에 연결한다. Excel은 DB나 판정의 원본이 아니라, 검토자가 결과를 확인하기 위한 화면 계약으로 유지한다.

## 중간 단계는 정확히 무엇인가요?

ReviewDocument는 여러 담당자가 함께 쓰는 **공통 문서 정리 양식**에 가깝습니다. XML adapter는 XML을 읽어 그 양식에 옮기는 코드이고, ReviewDocument는 옮겨 담긴 데이터입니다. JSON은 그 데이터를 파일로 저장할 때 사용하는 형식입니다.

여기서는 원문과 순서, 문단과 제목, 표의 행·셀, 목록과 하위 항목, 그림의 위치 관계, 언어, PDF 페이지와 XML 위치 등 확인 가능한 근거를 보존합니다. 근거가 없는 값은 추측해서 채우지 않습니다. 그림 구조가 보존됐다는 사실만으로 그림의 의미까지 알아냈다고 보지는 않습니다.

따라서 “중간 파싱·표준화 단계”라는 이해가 맞습니다. 문자 저장 방식을 바꾸는 인코딩보다, **추출된 문서를 여러 기능이 같은 방식으로 읽도록 정리하는 단계**라는 표현이 더 정확합니다.

다만 ReviewDocument 자체가 PDF를 더 정확히 추출해 주는 것은 아닙니다. XML에 이미 빠진 문장이 있으면 옮겨 담는 과정만으로 복원되지 않습니다. 추출기의 품질과 변환 과정의 보존 여부를 각각 검사해야 합니다.

## 왜 각 검토 기능이 XML을 직접 읽지 않나요?

예를 들어 XML에 구성품 목록이 있고 각 구성품 옆에 별표 조건 안내가 있다고 가정해 보겠습니다.

- 체크리스트 검토는 구성품 문구와 조건 안내 후보가 있는지 확인합니다.
- Before/After 비교는 구성품이 추가·삭제됐는지, 안내 문구가 달라졌는지 확인합니다.
- 사양 반영 검토는 회사 자료를 기준으로 해당 모델에 그 구성품이 적용되는지 확인합니다.

이들이 제각각 XML을 해석하면 어떤 기능은 목록 전체를 한 문장으로 읽고 다른 기능은 항목별로 읽을 수 있습니다. ReviewDocument가 목록의 항목 구분과 원문·근거를 공통으로 제공하면 각 기능은 자신의 검토 목적에 집중할 수 있습니다.

공통 자료를 사용해도 앞으로 추가하는 기능마다 필요한 정보와 지원 범위는 확인해야 합니다. 예를 들어 이미지 외형 비교에는 PDF 캡처가, 사양 검토에는 모델별 회사 기준값이 더 필요할 수 있습니다. 모든 기능이 추가 작업 없이 붙는다는 뜻은 아닙니다.

## 다국어 QA Agent는 어떤 역할인가요?

다국어 QA Agent는 자동 합격/불합격을 내리는 기능이 아닙니다. 번역·편집 업체에 확인 요청할 의심 지점을 정리하는 **참고 의견 전용** 기능입니다.

예를 들어 영어 기준 문구와 프랑스어 문구가 같은 의미인지, 문장 수가 1개에서 2개로 늘어도 의미가 유지되는지, 악센트·띄어쓰기·구두점·단어 붙음이 의심되는지를 표시합니다. `boîtierwireless`처럼 PDF 텍스트 레이어에서는 붙어 보이지만 MD/ReviewDocument에는 `boîtier Wireless`로 보존된 경우에는 “추출/표시 차이 가능성”으로 기록하고, 필요하면 업체 확인 요청 문장만 만듭니다.

이 Agent는 체크리스트 결과를 덮어쓰지 않습니다. 체크리스트 검토가 “필수 문구 후보가 있다”고 기록하더라도, 다국어 QA는 별도 열이나 별도 시트에 “번역 표현 확인 권장” 같은 참고 의견을 붙입니다. DB 수정, 번역 승인, 자동 Pass/Fail 판정은 하지 않습니다.

## Translation Base Profile

다국어 QA는 대상 언어를 아무 영어와 비교하면 안 됩니다. 어느 바이어가 어떤 영문 기준에서 번역되는지 알아야 잘못된 차이 지적을 줄일 수 있습니다.

기본 구조는 `buyer -> buyer_group -> english_base`를 권장합니다. 큰 권역별 그룹을 만들고, 그 그룹에 속한 buyer를 나열합니다. 예를 들어 호주 `XY`, 미얀마 `MR`, 인도네시아 `XD`, 동/서남아 `ASIA`가 같은 번역 기준을 쓴다면 아래처럼 관리할 수 있습니다.

```yaml
buyer_groups:
  A_ASIA:
    english_base: UK_ENG
    buyers:
      - XY
      - MR
      - XD
      - ASIA
```

다만 모든 buyer가 그룹 기본값을 따르지는 않을 수 있으므로 buyer별 예외를 허용합니다. 이 예외를 `override`라고 부릅니다.

```yaml
buyer_groups:
  NORTH_AMERICA:
    english_base: US_ENG
    buyers:
      - US
      - ZC

buyer_overrides:
  ZC:
    english_base: ZC_ENG
    reason: "캐나다용 영문 PDF 문구를 기준으로 C-FRA를 비교한다."
```

예를 들어 공통 북미 영어에는 `Contact Samsung Support for service.`가 있고, ZC 영문 PDF에는 `Contact Samsung Customer Care for service in Canada.`처럼 캐나다용 서비스 문구가 들어갈 수 있습니다. 이때 C-FRA가 실제로 ZC 영문을 번역한 것이라면 C-FRA는 `US_ENG`가 아니라 `ZC_ENG`와 비교해야 합니다. 그렇지 않으면 정상적인 캐나다 전용 문구를 의미 차이로 잘못 표시할 수 있습니다.

따라서 그룹은 반복 설정을 줄이는 기본값이고, override는 buyer 전용 영문 문장이 있는 경우를 위한 예외 처리입니다.

## 회사 시스템 값이나 모델 기준값은 미리 모두 줘야 하나요?

모든 정보를 처음부터 완벽히 줄 필요는 없습니다. 하지만 어떤 항목이 “고정 문구 확인”이 아니라 “모델명이나 회사 시스템 값으로 확인해야 하는 항목”인지는 반드시 표시되어야 합니다.

예를 들어 `Specifications` 안의 `Display Resolution`, `Sound (Output)`, `Operating Temperature`는 단순 문장 검색보다 모델별 기준값 비교에 가깝습니다. `S90H (42"): 20 W, S90H (48"-83"): 40 W`처럼 한 줄에 여러 모델 조건과 값이 들어 있으면 ReviewDocument는 원문·강조·항목명·값의 관계를 잃지 않고 보존해야 합니다. 실제 Pass/Fail은 후속 사양 검토 Agent가 회사 시스템에서 모델 기준값을 받은 뒤 판단합니다.

모델명 기준으로 확인해야 하는 문장도 같은 방식입니다. Bella가 모든 모델 규칙을 미리 작성하지 않아도, 최소한 “이 문장은 모델 조건에 따라 달라질 수 있음”이라는 표시가 있으면 시스템은 자동 확정하지 않고 `모델 기준값 필요` 또는 `사람/시스템 확인 필요`로 남길 수 있습니다. 반대로 그런 표시도 없고 외부 기준값도 없으면, 프로그램은 해당 문장을 고정 문구처럼 잘못 다룰 위험이 있습니다.

권장 입력 수준은 세 단계입니다.

| 단계 | 필요한 정보 | 시스템 처리 |
|---|---|---|
| 최소 | 이 항목은 모델/시스템 값 확인 대상이라는 표시 | 자동 판정하지 않고 확인 필요로 남김 |
| 권장 | 확인할 모델명, 사양 항목명, 회사 시스템에서 가져올 기준 필드 | ReviewDocument 근거와 시스템 값을 연결 |
| 운영 | 허용 단위·범위·예외 조건·모델군 규칙 | 사양 검토 Agent가 근거 포함 Pass/Fail 후보 생성 |

즉, 모든 값을 미리 줄 필요는 없지만 “이건 외부 기준값이 필요한 항목”이라는 신호는 미리 주는 편이 안전합니다. 그 신호가 있으면 ReviewDocument와 후속 Agent가 성급하게 고정 문구 판정을 하지 않습니다.

## 표준화와 검토 판정은 어떻게 다른가요?

| 단계 | 하는 일 | 하지 않는 판단 |
|---|---|---|
| XML 추출 | PDF의 글자와 구조를 읽음 | 체크리스트 충족 여부 |
| XML adapter / ReviewDocument | 추출된 원문·구조·근거를 공통 양식으로 보존 | 문구의 업무상 적절성, 합격·불합격 |
| 검토용 분류 | 필요할 때 근거에 따라 검토 목적 이름표를 붙임 | 기존 이름표 강제 적용, 근거 없는 의미 추측 |
| 검토 기능 | DB 또는 비교 대상과 대조하여 근거·차이·미확정 사유를 기록 | 미지원 항목의 임의 승인 |
| 결과 출력 | 결과 데이터를 검토자가 읽기 쉬운 Excel 등으로 표시 | 원문이나 판정의 임의 변경 |
| ReviewService | 추출·검토·출력을 순서대로 실행하고 실패와 완료를 관리 | 화면 배치 자체 |
| Streamlit 화면 | 입력을 받고 서비스를 호출하거나 결과를 보여 줌 | 화면 안에 별도 검토 규칙 보유 |

검토용 role은 현재 XML 구조와 검토 목적에 맞춰 정합니다. 예전의 `navigation_ui`, `spec_table`, `regulatory_note` 등은 필수 이름이 아닙니다. 현재 adapter는 업무 role을 강제로 부여하지 않습니다.

현재 체크리스트 연결은 문구 근거와 미지원 사유를 확인하는 파일럿입니다. 일반 체크 59건과 그중 구성품 상세 14건을 함께 보여 주며, 73개의 독립 체크로 합산하지 않습니다. 문구가 발견되어도 모델 적용이나 업무 합격을 자동 확정하지 않습니다.

## 지금 사람이 직접 확인할 부분이 상대적으로 적은 이유

이 단계의 확인 항목은 “원문이 그대로인가”, “표·목록의 경계가 보존됐는가”, “순서·언어·페이지 근거가 연결되는가”처럼 자동 대조가 가능한 것이 많습니다. 그래서 담당자가 XML과 JSON을 한 줄씩 읽거나 코드 연결 단계마다 승인할 필요는 상대적으로 적습니다.

그 대신 구현 담당자는 원문·구조·근거 보존, 잘못된 입력 거부, 실패 결과의 다운로드 차단, Excel 표시 값과 결과 데이터 일치를 자동 검사합니다. 자동 검사 통과는 검사한 범위에 대한 기술적 증거입니다.

사람이 확인하는 일은 다음처럼 구분합니다.

| 시점 | 담당자가 볼 자료와 질문 |
|---|---|
| 현재 표준화·실행 연결 개발 | 자동 대조로 확인 가능한 개발은 계속 진행. 원본 누락·구조·의미에 사람 확인이 필요하면 반드시 별도 요청 |
| 새 바이어·언어·레이아웃 도입 또는 추출 규칙 변경 | 원본 PDF와 MD를 대조. 누락·순서·표·그림 주변 관계가 맞는지 확인 |
| 최초 실제 사용 전 | 대표 PDF·MD·통합 Excel을 함께 확인. 해당 문구가 해당 체크의 근거인지, 보고서가 업무에 유용한지 확인 |
| 체크리스트 기준·모델 적용 조건 변경 | 작성용 Excel과 원본 근거를 보고 업무 담당자가 승인 |

**“지금 매 단계마다 사람이 볼 일은 적다”와 “사람 검토가 전혀 필요 없다”는 다른 이야기입니다.** 개발 연결은 계속 진행할 수 있습니다. 실제 업무에 사용하기 전에는 확인할 위치를 추린 PDF·MD·Excel 표본을 준비하여 담당자가 판단할 수 있게 합니다. 기존에 MD를 확인한 사실이 새 adapter와 최종 보고서까지 자동으로 승인하는 것은 아닙니다.

## 원문 위치와 체크리스트 번호

체크리스트 ID는 업무 기준을 가리키는 고정 번호입니다. XML 노드 ID는 해당 추출본 안의 위치를 찾는 참조이며 다시 추출하면 달라질 수 있습니다. 그래서 PDF 파일명과 추출본 식별 정보, 페이지, XML 위치를 함께 기록합니다.

언어별 문장 수를 똑같이 만들 필요도 없습니다. 영어 한 문단이 프랑스어 두 문단과 대응할 수 있으며, 향후 비교 기능이 여러 원문 단위를 하나의 요구사항에 연결하도록 설계합니다. 표준 문서에 담는 원문을 그 때문에 합치거나 번역하지 않습니다.

## 모든 바이어·언어 추출이 끝나야 설계할 수 있나요?

기본 설계와 전체 지원 확정을 나눠 진행합니다. 기본 설계는 지금도 가능하지만, 모든 조합에서 문제가 없다는 확정은 해당 범위의 검증 이후에만 가능합니다. 아직 추출하지 않은 언어가 있다는 이유로 공통 모델을 버리거나 모든 개발을 기다릴 필요는 없습니다.

현재 실물 adapter 보존 근거는 ZC의 ENG/C-FRA, XU의 ENG, ZG/XN/ZT 공통 프로필의 ENG/DEU/FRA/ITA/DUT입니다. 이 범위만으로 RTL(아랍어·히브리어), 한국어·중국어·태국어, 다른 BOOK의 구조까지 검증했다고 볼 수 없습니다. 다른 작업장에서 XML 추출이 끝났어도 v2 adapter의 검증 범위에는 자동으로 포함하지 않습니다.

설계 초기에 구조 차이가 큰 대표 사례를 우선 추가합니다. A2/A3/BOOK, LTR/RTL, 비라틴 문자, 중첩·병합 표, 그림과 문구 혼합, 공통 표지 등이 대상입니다. 대표 사례는 설계 결함을 일찍 찾기 위한 것이며 바이어별 원문 검수의 대체물이 아닙니다.

새 바이어·언어를 추출하면 XML의 원문·구조를 확인하고, 같은 추출본을 adapter로 변환하여 보존 여부를 자동 대조합니다. 새 구조를 표현할 수 없으면 원문을 기존 틀에 억지로 맞추지 않고 모델/adapter를 보완하며, 이미 검증한 표본도 다시 테스트합니다. 데이터 형식 변경이 필요하면 버전을 올리고 기존 결과 읽기 호환 또는 이관 절차를 명시합니다.

사람 확인이 필요한 원본 누락·읽는 순서·표/그림 관계 등은 PDF·MD와 확인할 페이지/항목을 지정하여 반드시 요청합니다. 확인자·날짜·바이어·언어·PDF 및 추출본 식별값·확인 범위를 [검증 대장](../migration/buyer-language-validation-ledger_kr.md)에 기록합니다. 전체 확인과 일부 항목 확인을 구분하고, 답을 받기 전에는 확인 완료로 기록하지 않습니다.

진행 순서는 **공통 모델 개발 → 구조가 다른 대표 사례 추가 → 바이어·언어별 추출과 변환 검증 반복 → 해당 범위 사람 확인 및 운영 적용**입니다. 각 단계는 병행할 수 있으나, 미확인 결과를 승인된 기준으로 사용하는 작업은 기다립니다.
