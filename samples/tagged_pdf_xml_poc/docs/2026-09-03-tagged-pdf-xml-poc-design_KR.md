# Tagged PDF XML 추출 POC 설계

## 1. 목적

이 프로젝트의 목적은 Tagged PDF에 포함된 논리 구조를 활용한 추출 방식이
레이아웃별 텍스트 추출 방식을 대체하여 새로운 매뉴얼 검토 시스템의 기반이
될 수 있는지 확인하는 것이다.

첫 번째 테스트 문서는 다음과 같다.

`C:\Users\bella\image-extractor\samples\SUG_RAW\0_TV_ZC\BN68-25100B-00_SUG_Y26 TV ALL_ZC_L02_260122.0.pdf`

이 PDF의 카탈로그에는 `/Marked true`와 `/StructTreeRoot` 항목이 모두 포함되어
있음을 이미 확인했다. 따라서 이 POC에서는 PDF 구조 트리를 읽기 순서와
계층 구조의 주된 기준으로 사용한다.

## 2. 프로젝트 경계

프로젝트는 `samples/tagged_pdf_xml_poc/`에 위치하며 기존 애플리케이션과
독립적으로 구성한다.

- 자체 `pyproject.toml`, 패키지 소스, 테스트, CLI 및 출력 디렉터리를 갖는다.
- 상위 프로젝트의 `src/` 패키지에 있는 모듈을 가져와 사용하지 않는다.
- CLI를 통해 임의의 PDF 경로를 입력받을 수 있으며 테스트 PDF를 복사하지 않는다.
- POC 기간에는 현재 Git 저장소 안에서 관리한다.
- POC가 통과하면 내부 import나 실행 인터페이스를 바꾸지 않고 이 디렉터리를
  새로운 저장소로 옮길 수 있어야 한다.

이 POC에서는 기존 추출 엔진, 체크리스트 데이터베이스, 비교 리포트 또는
Streamlit 애플리케이션을 수정하지 않는다.

## 3. 범위

### 포함 범위

- 입력 파일이 Tagged PDF인지 검증한다.
- 논리 구조 순서에 따라 `/StructTreeRoot`를 순회한다.
- 구조 요소와 marked-content 참조를 원본 텍스트로 해석한다.
- 문서, 파트, 섹션, 헤딩, 문단, 목록, 목록 항목, 표, 행, 헤더 셀 및
  데이터 셀과 같은 의미 역할을 보존한다.
- OSD 경로에 사용되는 유니코드와 의미 있는 특수문자를 보존한다.
- 원본 문자를 암묵적으로 변경하지 않으면서 PDF 텍스트 조각을 읽기 쉬운
  줄과 문장으로 연결한다.
- 원시 XML과 정규화 XML을 출력한다.
- 기계가 읽을 수 있는 추출 품질 리포트를 출력한다.
- 태그를 통해 추출된 텍스트의 커버리지를 독립적인 페이지 텍스트 기준과 비교한다.
- 해석되지 않은 참조, 지원하지 않는 태그, 빈 구조 요소, 중복 내용 및
  의심스러운 텍스트 누락 구간을 보고한다.

### 1단계 제외 범위

- XML에서 Markdown으로의 변환
- OCR
- 체크리스트 평가, 다국어 의미 비교 또는 리포트 UI
- 바이어별 또는 언어별 추출 규칙
- 원본 PDF 수정

## 4. 검토한 추출 방식

### A. 구조 트리 우선 추출 - 선택한 방식

PDF 논리 구조 트리를 읽고 marked-content 참조를 해석한다. 이 방식은 원본
PDF에서 작성된 계층 구조가 신뢰할 수 있는지를 직접 검증한다.

### B. 구조와 좌표를 결합한 추출

추출 과정에서 좌표 정보를 사용하여 태그 트리 결과를 보정한다. 개별 결과의
품질은 높일 수 있지만, 태그만으로 충분한지를 판단하기 어렵게 만들며 너무
이른 단계부터 프로필별 규칙이 다시 생길 수 있다.

### C. 좌표만 사용한 XML 생성

PyMuPDF 블록을 XML로 변환한다. 빠르게 구현할 수 있지만 Tagged PDF 활용
아이디어를 검증하지 못하므로 주 POC 방식으로 적합하지 않다.

선택한 설계에서는 의미 구조 출력에 A 방식을 사용한다. 좌표 또는 페이지
텍스트 추출은 독립적인 커버리지 측정에만 사용하며 암묵적인 보정 경로로는
사용하지 않는다.

## 5. 아키텍처

이 패키지는 POC에 필요하지 않은 프레임워크 계층을 추가하지 않으면서 작은
Clean Architecture 경계를 적용한다.

```text
src/tagged_pdf_extractor/
  domain/
    models.py             문서 트리, 요소, 콘텐츠 조각, 진단 정보
  application/
    extract_document.py   유스케이스와 추출 결과
    evaluate_quality.py   커버리지 및 구조 품질 평가
  ports/
    pdf_reader.py         추상 Tagged PDF 리더 계약
    output_writer.py      추상 출력 계약
  infrastructure/
    pypdf_reader.py       PDF 객체/트리 및 marked-content 구현
    pymupdf_baseline.py   독립적인 페이지 텍스트 커버리지 기준
    xml_writer.py         원시 XML 및 의미 XML 직렬화
    json_report_writer.py 품질 리포트 직렬화
  cli.py                  명령줄 구성 루트
```

의존성은 안쪽을 향한다. Domain과 Application 모듈은 PDF 또는 XML 라이브러리를
가져오지 않는다. Infrastructure는 Port 계약을 구현한다. CLI만 전체 객체를
조립하는 구성 루트 역할을 한다.

## 6. 데이터 흐름

```text
PDF 경로
  -> Tagged PDF 검증
  -> 구조 트리 순회
  -> marked-content 해석
  -> 불변 문서 트리
  -> 보수적인 텍스트 연결
  -> 의미 XML
  -> 기준 텍스트 비교
  -> 품질 리포트
```

두 개의 XML 파일을 생성한다.

- `raw_structure.xml`: 진단에 필요한 원본 태그 이름, 객체 참조, MCID,
  페이지 참조, 속성 및 수정하지 않은 해석 결과 조각을 포함한다.
- `semantic_document.xml`: 사람이 검토하거나 후속 처리에 사용할 수 있도록
  정규화한 의미 요소 이름과 보수적으로 연결한 텍스트를 포함한다.

의미 XML에서 텍스트 조각을 연결하더라도 원본 조각은 원시 XML에 남긴다.
따라서 모든 정규화 과정은 추적 가능하고 되돌릴 수 있어야 한다.

## 7. 텍스트 보존 규칙

- PDF 텍스트를 ASCII로 음역하지 않고 유니코드로 디코딩한다.
- XML 예약 문자는 직렬화할 때만 이스케이프한다. XML을 다시 파싱하면 원래
  문자가 복원되어야 한다.
- `>`, `→`, `/`, `&`, `:`, 대괄호, 괄호, 모델 코드, 단위 및 문장부호를
  그대로 보존한다.
- 기호를 추정한 다른 기호로 정규화하지 않는다.
- 명시적이고 보수적인 규칙으로 하이픈이 레이아웃상의 인위적인 문자임을
  입증할 수 있을 때만 줄바꿈 하이픈을 제거한다. 그 외에는 보존한다.
- 논리 태그 순서, 공백 근거 및 문장부호에 따라 텍스트 조각을 연결한다.
  원본 텍스트를 재구성하는 데 LLM을 사용하지 않는다.
- 공백을 변경하는 모든 연결 판단을 품질 리포트에 기록한다.

## 8. 의미 구조 매핑

알려진 PDF 표준 구조 유형은 다음과 같이 매핑한다.

| PDF 태그 | 의미 XML |
| --- | --- |
| `Document` | `document` |
| `Part`, `Art`, `Sect`, `Div` | 동일한 역할명의 소문자 형태 |
| `H`, `H1`-`H6`, `Title` | 원본 역할과 레벨을 포함한 `heading` |
| `P` | `paragraph` |
| `L`, `LI`, `Lbl`, `LBody` | 목록 계층 요소 |
| `Table`, `TR`, `TH`, `TD` | 표 계층 요소 |
| `Figure`, `Caption` | 그림/캡션 요소 |
| 알 수 없는 역할 | 정확한 원본 역할을 보존한 `unknown` |

PDF RoleMap 별칭을 먼저 해석한 다음 의미 구조에 매핑한다. 알 수 없는 태그로
인해 콘텐츠가 유실되어서는 안 되며 해당 태그는 경고로 표시한다.

## 9. 오류 처리

읽을 수 없는 PDF, 구조 트리 누락, 트리 순회를 막는 잘못된 객체 참조 또는
출력 쓰기 실패가 발생하면 CLI는 0이 아닌 종료 코드를 반환한다.

지원하지 않는 역할, 빈 요소, 해석되지 않은 단일 MCID 또는 커버리지 누락과
같이 복구 가능한 결함은 진단 정보로 남기고 추출을 계속한다. 리포트에 표시하지
않은 fallback 콘텐츠를 의미 XML에 삽입해서는 안 된다.

출력은 실행별 임시 디렉터리에 먼저 기록하고, 필요한 모든 산출물이 성공적으로
직렬화된 후에만 요청한 출력 디렉터리로 이동한다. 명시적인 CLI 옵션을 지정하지
않으면 기존 출력 파일을 덮어쓰지 않는다.

## 10. 출력

최초 테스트 문서의 기본 출력 디렉터리는 다음과 같다.

`outputs/BN68-25100B-00/`

필수 산출물은 다음과 같다.

- `raw_structure.xml`
- `semantic_document.xml`
- `extraction_report.json`

리포트에는 PDF 태그 메타데이터, 요소 수, 헤딩 계층, 특수문자 검사,
태그 텍스트 커버리지, 해석되지 않은 참조 수, 알 수 없는 역할, 공백 연결 기록
및 최종 게이트 상태가 포함된다.

## 11. 품질 게이트

최초 실행은 다음 하드 게이트를 모두 통과해야 성공으로 판단한다.

- PDF가 marked 상태이며 구조 트리를 가지고 있다.
- 치명적인 순환 참조나 손상된 루트 없이 구조 트리 순회가 완료된다.
- 헤딩 요소와 본문 콘텐츠 요소가 각각 하나 이상 복원된다.
- 해석된 원본 텍스트가 XML 직렬화 과정에서 유실되지 않는다.
- XML 파일이 올바른 형식이며 왕복 파싱에 성공한다.
- 원본 조각에서 발견된 필수 OSD 경로 문자가 의미 XML 직렬화 후에도 정확하게
  보존된다.
- 해석되지 않은 모든 MCID 또는 객체 참조를 집계하고 식별할 수 있다.

최초 실행에서는 다음 항목에 고정 합격 기준을 적용하지 않고 측정 결과로 보고한다.

- 페이지 텍스트 추출 결과 대비 태그 텍스트 커버리지
- 빈 구조 요소 비율
- 알 수 없는 역할의 수
- 의심스러운 문장 조각 및 공백 연결의 수

첫 번째 실제 출력물을 검토한 후, 미리 추측한 값이 아니라 실제 근거를 바탕으로
수치 기반 합격 기준을 정의한다.

## 12. 테스트 전략

- 구조 역할 매핑, RoleMap 별칭, XML 이스케이프, 유니코드/특수문자 왕복 처리
  및 보수적인 텍스트 조각 연결에 대한 단위 테스트
- 트리 순회, 중첩 헤딩, 목록, 표, 알 수 없는 역할 및 손상된 참조를 검증하는
  소형 생성 PDF 또는 수작업 PDF 객체 fixture 기반 어댑터 테스트
- 지정한 ZC PDF를 사용하는 통합 테스트. 외부 샘플 경로가 없으면 명시적인
  사유와 함께 건너뛴다.
- Application 코드가 Port에만 의존하며 상위 `src` 패키지를 가져오지 않는다는
  것을 증명하는 계약 테스트
- 정상 추출, 태그 누락, 잘못된 입력, 출력 충돌 및 리포트 생성을 검증하는 CLI 테스트

## 13. POC 이후 결정

사람이 결과를 검토했을 때 헤딩, 계층 구조, 문장 연속성, 표/목록 및 OSD 경로가
현재의 레이아웃 규칙 기반 방식보다 실질적으로 더 신뢰할 수 있다고 확인된 경우에만
이 프로젝트를 새로운 매뉴얼 검토 시스템의 추출 기반으로 사용한다.

태그가 불완전하지만 유용한 경우에는 이후 별도 설계를 통해 명시적인 보정 단계를
추가할 수 있다. 해당 결정은 이 POC의 범위를 벗어나며 최초 추출기 내부에 숨겨진
형태로 포함해서는 안 된다.
