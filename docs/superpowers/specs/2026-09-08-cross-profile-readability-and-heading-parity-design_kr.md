# 바이어 공용 가독성 및 다국어 헤딩 동등성 설계

## 목표

언어별 문구 사전이나 바이어별 제목 하드코딩 없이 다음 기능을
개선합니다.

1. 실제 문장 경계는 표시하되 공백이 포함된 약어는 분리하지 않습니다.
2. 충분한 구조·글꼴·위치 근거가 있는 목록 보충 문단만 앞 불릿에
   연결합니다.
3. 제목과 괄호 설명이 한 문단에 들어간 굵은 표 소제목도 탐지합니다.
4. 메타데이터상 언어가 2개 이상인 모든 PDF에서 언어별 헤딩 구조가
   동일한지 검증합니다.

원문은 변경하지 않습니다. Markdown 검토와 향후 문장 단위 Excel 출력에
사용할 수 있는 표시 및 검증 근거를 추가합니다.

## 적용 범위

판별기는 모든 바이어와 문자 체계에서 재사용할 수 있는 공용 코드로
구현합니다. 다만 필요한 구조·글꼴·위치 근거가 모두 확인된 대상에만
작동합니다. 근거가 누락되거나 애매하면 기존 구조를 그대로 유지합니다.

최초 실물 PDF 검증 대상은 다음과 같습니다.

- `ZG XN ZT_L05` BOOK: ENG, DEU, FRA, ITA, DUT
- `ZC_L02` A2: ENG, C-FRA
- `LATIN_L02` A2: ENG, M-SPA
- 단일 언어 비적용 대조군: `KR_KOR` 및 `XY_ENG` 또는 `XU_ENG`

다국어 헤딩 검증은 BOOK뿐 아니라 메타데이터의 `language_count >= 2`인
BOOK, L02, 언어 조합 시트 모두에 적용합니다. 단일 언어 PDF에는 언어 간
동등성 결과를 만들지 않습니다.

OCR, 문서 코드 비교, 번역 의미 비교, 번역 제목 사전, 체크리스트 DB 수정,
Excel 출력 구현은 이번 범위에 포함하지 않습니다.

## MCID 위치 근거

MCID는 PDF 구조 노드와 실제 화면 콘텐츠를 연결하는 문서 내부 번호입니다.
현재는 MCID의 페이지·글자·글꼴을 보존하지만 일반 텍스트의 위치는 보존하지
않습니다.

앞으로 각 글자 조각에 선택적 BBox를 추가합니다.

```text
page_index
mcid
text_parts
text_styles
bbox = (왼쪽, 위쪽, 오른쪽, 아래쪽)
```

PDF 콘텐츠 스트림을 해석할 때 실제 글자 위치를 수집합니다. OCR이나 이미지
추정은 사용하지 않습니다. 하나의 MCID에 화면 글자 묶음이 여러 개면 전체
영역을 포함하는 합집합 BBox를 계산합니다. 문단과 List Body의 BBox는 같은
페이지에 있는 하위 MCID BBox를 합쳐 계산합니다.

유효 좌표가 없거나 여러 페이지에 걸친 경우에는 위치가 필요한 판별을 하지
않습니다. BBox는 Raw XML과 Semantic XML에 근거로 기록하지만 Markdown에는
표시하지 않습니다. 잘못된 좌표는 검증 오류로 처리하고, 선택적 좌표가 없다는
이유만으로 전체 텍스트 추출을 실패시키지는 않습니다.

## 문장 경계 정책

문장 경계는 원문 수정이 아니라 표시 근거입니다. Markdown에서는 동일한
구조 안에 `<br>`로 표시하고, 향후 Excel에서는 같은 근거를 이용해 `<br>`
문자 없이 문장별 행으로 출력할 수 있습니다.

기존의 List Body와 표 셀뿐 아니라 일반 leaf 본문 문단까지 적용합니다.
leaf 본문은 글자와 인라인 요소만 있고 내부에 목록·표·그림·헤딩·라벨 같은
블록 구조가 없는 최종 문단입니다.

다음 대상은 제외합니다.

- 원본 또는 승격 헤딩
- 굵은 소제목과 라벨
- 캡션과 그림 내부 텍스트
- URL, 이메일, 소수점, 버전, 규격, 파일명 및 모델명 토큰
- 다음 글자가 명확한 문장 시작으로 판단되지 않는 경우

`z. B.`와 NBSP가 포함된 같은 형태는 단일 문자와 마침표가 두 번 이상
이어지는 Unicode 구조로 보호합니다. 약어 문구나 언어명은 코드에 넣지
않습니다.

이를 통해 DEU `z. B.` 내부의 잘못된 `<br>`은 제거하고, 검토된 DEU/FRA
일반 본문의 실제 두 문장 사이에는 `<br>`을 추가합니다.

## 보충 문단 연결

두 List 사이의 독립 P는 다음 조건을 모두 만족할 때만 앞 List Item의 보충
문단으로 표시합니다.

- 의미 있는 형제 구조가 `List -> P -> List`
- 같은 섹션·언어 구간·페이지
- P가 목록 계열 source role을 가지지만 자체 불릿·번호·헤딩 표시는 없음
- 앞 List Body와 글꼴 크기 및 굵기가 같음
- P의 왼쪽 위치가 불릿 기호가 아닌 앞 List Body 글자 위치와 허용 오차
  안에서 일치
- 앞 List Body와의 수직 간격이 해당 영역의 목록 줄 간격에 부합하고 독립
  블록과의 간격보다 가까움
- 한 페이지의 완전하고 유효한 위치 근거가 있음
- 헤딩·소제목·굵은 라벨·기존 승격 정보와 충돌하지 않음

`List -> P -> List` 순서만으로는 절대 연결하지 않습니다. 조건 하나라도
확인할 수 없거나 애매하면 독립 문단으로 남깁니다.

Semantic XML에는 대상 P와 앞 List Item, source role, 글꼴 근거, 왼쪽 위치
차이 및 수직 간격을 기록합니다. Raw 구조는 바꾸지 않습니다. Markdown은
새 불릿을 만들지 않고 앞 불릿 아래에 들여쓰기해 표시합니다.

FRA 전원 사양 참조 문단을 최초 양성 사례로 사용합니다. 문구를 비교하지
않고 ZG 5개 언어의 같은 구조를 확인합니다. ZC·LATIN·KR·XY/XU에서는
오연결이 없는지 검증한 뒤 공용 판별기로 확정합니다.

## 한 문단형 표 소제목 복원

현재는 그림 셀 옆 텍스트 셀에서 굵은 제목 P와 괄호 설명 P가 별도 형제로
제공되는 구조를 탐지합니다. 다음 대체 구조도 지원합니다.

```text
그림 셀 | 하나의 leaf P 안에 굵은 제목 + 명시적 줄바꿈 + 괄호 설명
```

기존의 그림 셀, 뒤따르는 본문, 상대 글꼴 굵기, 길이 및 충돌 방지 조건을
그대로 적용하면서 다음 조건을 추가합니다.

- 원본 인라인 줄바꿈이 두 개의 비어 있지 않은 구간을 나눔
- 첫 구간이 뒤따르는 본문보다 굵음
- P 내부에 블록 구조가 없음
- 문장부호나 문구가 아니라 원본 줄바꿈이 분리 근거임
- 혼합 글꼴이나 후보 줄바꿈이 여러 개면 적용하지 않음

Semantic XML에는 굵은 제목 범위와 괄호 설명 경계를 기록합니다. Markdown은
제목을 굵게 하고 괄호 설명은 다음 줄에 표시합니다. ITA 폐기 제목을 양성
사례로 사용하고, 이미 정상인 별도 P 구조는 변경하지 않습니다.

## 다국어 헤딩 동등성

프로필은 `metadata/pdf_profile_mapping/pdf_profile_mapping.json`을 사용합니다.
폴더명과 신뢰하기 어려운 문서 `/Lang` 값은 운영 메타데이터로 사용하지
않습니다.

`language_count >= 2`이면 기존 언어 구간 근거를 사용합니다.

- BOOK: PDF 북마크 기반 언어 구간과 순서
- L02 및 언어 조합 시트: 기존 페이지/언어 구간 근거와 프로필 언어 순서

각 언어 구간에서 문구를 제외한 헤딩 서명을 문서 순서로 만듭니다.

```text
(헤딩 레벨, 원본 헤딩/번호 승격 구분, 번호 라벨 또는 null)
```

검증 보고서에는 다음을 기록합니다.

- 예상 언어 수와 발견된 언어 구간 수
- 언어별 전체 헤딩 개수
- 언어별 헤딩 레벨 순서
- 원본 헤딩과 번호 승격의 순서
- 언어별 번호 라벨 순서
- 누락되거나 추가된 헤딩 위치

예상 언어 구간 수, 번호 순서, 번호 시리즈 개수 및 전체 헤딩 서명이 언어별로
같아야 hard gate를 통과합니다. 향후 실제 원장이 언어별로 다르다는 근거가
확인되면 PDF 증거가 있는 명시적 프로필 예외로 처리하며, 공용 검증기를
자동으로 느슨하게 만들지 않습니다.

현재 ZG의 예상값은 언어별 전체 26개, `H2=9`, `H3=8`, `H4=9`입니다. ZC와
LATIN은 각 파일 내부의 두 언어끼리 동등성을 검증합니다. ZG와 절대 헤딩
개수가 같을 필요는 없습니다.

## 구조와 데이터 흐름

1. PDF 인프라가 MCID 글자·글꼴·선택적 BBox를 수집합니다.
2. 불변 TaggedDocument가 위치 근거를 보존합니다.
3. 공용 도메인 판별기가 문장·보충 문단·소제목 힌트를 만듭니다.
4. 프로필 메타데이터는 다국어 헤딩 검증 적용 여부만 결정하며 번역 문구를
   선택하지 않습니다.
5. Semantic XML이 판별 근거와 표시 힌트를 직렬화합니다.
6. 품질 평가기가 언어별 헤딩 서명과 힌트 무결성을 검증합니다.
7. Markdown Writer는 검증된 XML 근거만 표현하고 위치나 프로필을 다시
   판별하지 않습니다.

판별 로직은 Markdown Writer에 넣지 않습니다. 기존 호환 진입점과 필수 출력
파일 4개의 형식은 유지합니다.

## 실패 및 안전 정책

- 위치가 없거나 잘못됨: 독립 문단 유지
- 약어인지 애매함: 임의 `<br>` 추가 금지
- 소제목 분리가 애매함: 일반 텍스트 유지
- 프로필 또는 다국어 구간을 찾지 못함: 진단 기록 후 해당 동등성 게이트
  실패, 언어 구간 추측 금지
- 중복·겹침·미해결·페이지 교차·구조 충돌 힌트: 원자적 출력 발행 중단
- 추론된 표시 구조를 흉내 내기 위해 원문이나 Raw 구조를 수정하지 않음

## 검증

구현 전에 다음 실패 테스트를 작성합니다.

- `z. B.` 및 NBSP 변형이 분리되지 않음
- 일반 leaf 본문의 실제 두 문장은 분리됨
- 헤딩·라벨·URL·모델/규격 토큰·블록 포함 문단은 제외됨
- 근거가 완전한 보충 P만 앞 불릿에 연결됨
- 순서만 맞거나 위치·글꼴·페이지가 다른 P는 독립 상태 유지
- 한 문단형 굵은 제목/괄호 설명은 탐지되고 애매한 분리는 거부됨
- 언어 구간 수, 전체 헤딩 서명, 레벨 순서, 번호 라벨 불일치가 각 게이트를
  실패시킴
- 단일 언어 프로필은 동등성 비교에서 제외됨

실물 PDF 회귀에서는 ZG·ZC·LATIN을 다시 생성하고 표시된 DEU/FRA/ITA
구간을 확인합니다. 단일 언어 대조군에서 보충 문단 오연결과 헤딩 동등성
오적용이 없어야 합니다. 마지막으로 POC 전체 테스트와 저장소 루트의
`python -m compileall src tests scripts apps`를 실행합니다.
