# 전 바이어 공용 인라인 아이콘 판별 설계

## 상태

2026-09-07 검토에서 승인한 방향이다. 이 문서는 `samples/tagged_pdf_xml_poc`의 다음 변경 범위를 정의한다.

## 문제

현재 판별기는 태그된 빈 `Figure`의 BBox가 바로 앞뒤 글자 크기에 비해 작을 때만 `[아이콘]`으로 표시한다. 대부분의 인라인 그림에는 작동하지만, PDF가 인접 글자 크기를 `1.0 pt`처럼 비정상적으로 제공하면 실제 OSD 경로 아이콘을 놓친다. 그래서 같은 메뉴 경로 안에 있는 동일한 9 x 9 그림도 서로 다르게 분류된다.

규칙은 바이어·레이아웃·언어에 상관없이 작동해야 한다. source token, 바이어명, 언어, 번역 문구, 아이콘 이름 또는 고정 본문 글자 크기에 의존하지 않는다.

## 전 바이어에서 관찰한 근거

생성된 semantic XML에서 ZG, ZC, KR, ZA, XY 모두 다음 구조를 사용한다.

```text
([그림] > 방향 설명 > [그림] 설정 > 고객지원 > ...)
```

언어별 단어는 달라도 태그된 그림의 위치와 반복되는 `>` 구분자는 유지된다. 괄호는 자주 있지만 필수로 삼을 수 없다. 일부 경로는 괄호 없이 아이콘으로 바로 시작하기 때문이다. 일반 문장과 그림 설명에도 괄호가 있으므로 괄호만으로는 충분한 근거가 아니다.

현재 산출물에서 측정한 근거는 다음과 같다.

- ZG: 반복된 `>` 경로에 속한 그림 100개 중 현재 인접 글자 크기 규칙이 35개를 놓친다.
- ZC: 같은 구조의 그림 20개 중 15개를 놓친다.
- KR: 같은 구조의 그림 16개 중 13개를 놓친다.
- ZA·XY 산출물도 같은 경로 구조를 포함한다. 다만 해당 산출물은 현재 아이콘 annotation 기능보다 먼저 생성되었다.

ZG의 일부 경로 그림은 9 x 9가 아니라 약 24 x 9이다. 따라서 일반 아이콘용 너비 제한만 사용하면 가로로 긴 리모컨·버튼 아이콘도 누락된다.

## 목표

- 문구와 무관한 구조적 근거로 OSD·메뉴 경로 아이콘을 판별한다.
- Wall-anchor, 스위치 아이콘처럼 메뉴 경로가 아닌 인라인 아이콘에는 공용 fallback을 유지한다.
- 독립 그림, 안전 심볼 표, 제품 도해와 판별이 불확실한 그림에는 보수적인 처리를 유지한다.
- semantic XML에 사람이 추적할 수 있는 판별 근거를 보존한다.
- 바이어별 dispatch 없이 모든 프로필에 같은 알고리즘을 적용한다.

## 제외 범위

- 아이콘을 홈·설정·볼륨 등의 이름으로 판별하는 기능
- OCR 또는 이미지 유사도 판별
- 블록 시작 위치의 `\[아이콘]:` 같은 Markdown escape 변경
- 최종 Excel 문장 exporter 구현. Markdown의 `<br>`는 계속 표시 전용이며 이번 변경 범위가 아니다.

## 검토한 접근법

### 1. 문장부호만 사용

`>`, `(` 또는 `)`가 있는 문단의 모든 그림을 아이콘으로 처리한다.

문장부호가 해당 그림과 무관할 수 있고 괄호가 일반 문장에도 많으며, 큰 삽화를 차단할 크기 근거가 없으므로 채택하지 않는다.

### 2. 현재 크기 제한만 완화

인접 글자 기준은 유지하면서 허용 너비와 높이만 늘린다.

비정상 인접 글자 크기라는 근본 원인이 남고 일반 그림의 오탐 가능성이 커지므로 채택하지 않는다.

### 3. 구조 + 상대 크기의 이중 판별

채택한다. 신뢰도 높은 OSD 경로 판별과 더 엄격한 일반 인라인 판별을 나눈다. 두 판별 모두 공통 원본 무결성 조건을 먼저 통과해야 한다.

## 확정 설계

### 공통 필수 조건

다음 조건을 모두 만족하는 그림만 아이콘 후보로 검토한다.

- 기존 `span`·`link` wrapper를 포함해 인라인 `paragraph` 또는 `list_body` 흐름 안에 있다.
- 그림이나 하위 ActualText에 화면에 보이는 추출 문자가 없다.
- 하나의 명확하고 양수이며 유한한 BBox가 있다.
- page index가 유효하다.
- 근거가 되는 글자가 같은 페이지에 있다.
- 표·헤딩·캡션·라벨·중첩 목록·독립 그림 같은 구조 경계를 넘어 근거를 가져오지 않는다.

하나라도 실패하면 일반 그림으로 유지한다.

### 경로 A: OSD·메뉴 경로 아이콘

기존 인라인 흐름에서 각 그림 주변의 로컬 token 구간을 만든다. 다음을 만족하면 강한 메뉴 경로 근거로 본다.

1. 가장 가까운 좌우 글자 token 중 한쪽 이상이 공백 정규화 후 ASCII `>`로 시작하거나 끝난다.
2. 같은 연속 흐름 구간에 `>`가 최소 2개 있고, 문장부호가 아닌 실제 글자 token이 최소 1개 있다.
3. 해당 구간에 구조 경계나 페이지 전환이 없다.

구간을 감싸는 균형 잡힌 `(`와 `)`는 신뢰도를 높이는 감사 근거로 기록하지만 필수는 아니다. 괄호 하나 또는 `>` 하나만으로는 경로 A를 통과하지 않는다.

부모 문단 전체에 `>`가 있는지만 보지 않고 그림별 로컬 token 구간을 검사한다. 그래야 긴 문장 멀리 있는 비교 기호 하나가 문단 속 모든 그림을 아이콘으로 만드는 오탐을 막을 수 있다.

이 경로에서는 글자 크기를 결정 조건이 아니라 보조 안전 조건으로 사용한다. 기준 글자 크기는 같은 페이지의 연속 경로 구간에 있는 유효한 글자 스타일 전체를 대상으로, 화면에 보이는 글자 수로 가중한 중앙값을 사용한다. 그러면 인접한 `1.0 pt` 조각 하나가 결과를 지배하지 못한다. 가로로 긴 인라인 버튼 아이콘을 허용하되 세로 크기는 보수적으로 제한한다. 최초 검증값은 다음과 같다.

- 최대 너비/기준 글자 크기 비율: `5.0`
- 최대 높이/기준 글자 크기 비율: `2.5`

신뢰할 수 있는 구간 기준 글자 크기를 계산하지 못하면 아이콘으로 추정하지 않고 일반 그림으로 유지한다. 고정 pt값 fallback은 추가하지 않는다.

### 경로 B: 일반 인라인 아이콘

강한 메뉴 경로 근거가 없는 그림에는 현재의 보수적 판별을 유지한다.

- 좌우 중 한쪽 이상에 화면에 보이는 글자가 바로 인접한다.
- 글자와 그림이 같은 페이지에 있다.
- 최대 너비/기준 글자 크기 비율은 `3.0`이다.
- 최대 높이/기준 글자 크기 비율은 `2.0`이다.

기준 글자 크기는 후보의 연속 인라인 구간에 있는 유효한 글자 전체로 계산하도록 개선한다. 바로 앞뒤 글자는 그림이 인라인이라는 근거로는 유지하지만, 비정상적인 한 조각이 기준 크기 전체를 결정하지 않게 한다.

이 경로는 특정 문구를 사용하지 않고 Wall-anchor, 스위치, 짧은 범례 아이콘 등을 처리한다.

### 판별 사유와 XML 근거

`InlineIconHint.reason`으로 두 경로를 구분한다.

- `navigation_route_inline_figure`
- `small_inline_figure_with_adjacent_text`

Semantic XML에는 기존처럼 BBox, 기준 글자 크기, 너비·높이 비율을 기록한다. 메뉴 경로 판별에는 구분자 개수와 균형 잡힌 괄호 존재 여부도 감사 근거로 기록한다. Markdown은 두 사유 모두 이름을 추정하지 않고 동일한 `[아이콘]`으로 표시한다.

Markdown reader는 판별 사유별 허용 크기 비율을 검증하고, 직렬화된 근거가 domain 판별을 다시 실행한 결과와 같은지 확인한다. 알 수 없는 사유나 모순된 근거가 있으면 출력을 발행하지 않는다.

## 데이터 흐름

```text
태그 구조
  -> 인라인 흐름 token
  -> 공통 원본 무결성 검사
  -> 로컬 메뉴 경로 근거 검사
       -> 경로 A 상대 크기 안전 검사
     해당하지 않으면
       -> 경로 B 일반 상대 크기 검사
  -> 사유와 근거를 가진 InlineIconHint
  -> semantic XML 표시 속성
  -> Markdown [아이콘] 또는 일반 그림 fallback
```

Raw 태그 구조와 원문 텍스트는 수정하지 않는다.

## 오류 처리와 보수적 fallback

- BBox 누락·충돌·형식 오류·무한값: 일반 그림
- 글자 스타일 누락 또는 내부 불일치: 일반 그림
- 그림이나 ActualText에 보이는 글자가 있음: 글자 복원을 우선하고 일반 그림
- `>` 하나, 반복 경로가 없는 불완전 괄호, 멀리 떨어진 관련 없는 `>`: 경로 A를 사용하지 않고 일반 경로만 검토
- domain 판별, XML 근거, Markdown 검증이 불일치함: 조용히 분류를 바꾸지 않고 출력 발행 실패

## 검증

### 단위 테스트

- 괄호가 있는 경로와 없는 경로의 처음·중간·마지막 아이콘 판별
- 언어 문구와 무관한 메뉴 경로 fixture 판별
- `>` 하나, 일반 괄호, 수학·비교 문장, 멀리 떨어진 구분자가 경로 A를 작동시키지 않음을 확인
- 인접한 `1.0 pt` 이상값이 경로 구간의 대표 글자 크기를 덮어쓰지 않음을 확인
- 검증된 9 x 9 및 24 x 9 경로 아이콘 허용
- 경로 A의 너비·높이 제한을 넘는 그림 거부
- Wall-anchor 형태의 기존 일반 아이콘 판별 유지
- 독립 그림, 표·안전 심볼 그림, 다른 페이지 근거, 그림 내 글자, 잘못된 속성 거부
- 두 판별 사유와 근거가 XML 및 Markdown 검증을 통과하는지 확인

### 실물 PDF 회귀

- 자동 추출·회귀: ZG, ZC, KR, ZA, XY
- 사람의 Markdown/PDF 표본 확인: 현재 검토 범위에 따라 ZG, ZC, KR
- 기존 문장 줄바꿈, 특수문자, 헤딩, 목록, 표, RF 형식, DoC 형식이 변하지 않았는지 확인
- semantic model, semantic XML, Markdown의 아이콘 개수가 같은지 확인
- 모든 보고서가 `status=pass`를 유지하는지 확인

## 완료 조건

- 문의한 ZG OSD 그림이 같은 메뉴 경로 안에서 모두 일관되게 `[아이콘]`으로 표시된다.
- ZC, KR, ZA, XY의 동등한 경로가 동일 코드로 처리된다.
- source token, 바이어, 언어, 메뉴 문구, 번역 문구 또는 고정 글자 크기 dispatch를 추가하지 않는다.
- 기존 일반 인라인 아이콘 판별이 유지된다.
- 불확실하거나 독립된 그림은 `[그림: 텍스트 없음]`으로 남는다.
- 관련 단위 테스트, 실물 PDF 회귀, `python -m compileall src tests`가 통과한다.
